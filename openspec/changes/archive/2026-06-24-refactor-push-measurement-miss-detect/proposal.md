## Why

目前藍芽量測流程因背負「發 CD 主動要資料」的歷史設計而過度複雜，且實測證明 CD 在生產線無效（CD 只回快取值、不觸發新量測）。更嚴重的是：汽缸一次壓 6 支，若某支沒壓到（漏壓），現行流程會「無限重試等資料」或沿用該支上一輪舊值，導致流程卡死或漏壓零件被誤判 PASS、操作員無法察覺。

實測（`cb_test/`）已確認耳溫槍行為：只在實體壓桿觸發才主動推送量測值、閒置不推、CB(ACK) 非必要。據此可大幅簡化通訊並改用「純主動推送 + 新鮮度偵測」可靠地抓出漏壓。

## What Changes

- **生產取值改為純主動推送**：D515/D500=1 觸發後不再發 CD，改用各通道在本輪觸發後產生的新推送值放入空槍值/量測值。
- **「無限重試」改為「timeout 放行」**：現行「收不到值就每 0.5s 無限重試」改為等待 timeout（預設 3 秒、可調）；到期仍未收到新推送的啟用通道即判定為漏壓並放行判定，不再卡流程。
- **新增漏壓偵測與處理**（單支標記，其他通道照常判定）：
  - 漏壓通道**不寫值（留 None）、不沿用舊值**。
  - 該通道 **D501~D512 寫 NG(1)** → PLC 既有邏輯把該耳溫套噴到 NG port。
  - 寫 **D513 bit15 = ON** → PLC 既有「D513≠0 即暫停」邏輯讓機台停下等人處理。
  - HMI 跳警報：`未收到量測值: CHx（未壓到/未觸發）`。
  - **CSV/遠端 log**：漏壓通道欄位**留空白**（與「停用通道寫 0」區分）；log 的格式、路徑、檔名、非同步佇列一律不變。正常循環的 log 內容完全相同。
  - 設定/清除時機與既有 bit12（溫度異常）/13（連續無套）/14（空槍異常）對齊：皆在收集判定階段、寫 PLC 結果與 reset D500/D515 之前完成；由異常復歸（D513 全清）清除。差異僅在觸發條件——12/13/14 是「值收齊即判」，bit15 是「等到 timeout 仍缺即判」。
- **漏壓也照常完成握手**：判定 + 寫 PLC/LOG 後一律把 D500/D515 歸 0，流程不卡死；機台暫停由 D513 bit15 獨立負責，操作員按異常復歸後恢復。
- **保留 CD 僅供手動模式**：UI「手動擷取」（直接寫 D515/D500、無實體壓桿）需發 CD 取快取值；以**明確的手動旗標**區分手動 vs 生產，避免「整台汽缸失效全漏壓」被誤判成手動。
- **移除 CB**：`send_ack`/`build_cb_response` 確認不需要（不送槍照常運作），清除死碼。

> PLC 端**不需改梯形圖**：暫停（D513≠0）與噴 NG port（D501~D512=1）都是既有行為，本變更只是在漏壓時正確寫入這兩個既有暫存器。

## Impact

- `bluetooth_comm.py`: 移除/縮減 CD 相關（`request_measurement` 僅手動用）、移除 CB 死碼、`_cd_sent_at`/`consume_cd_flag` 視情況保留或簡化。
- `main.py`: 重寫 `_acquire_and_collect`／`collect_empty_values`／`collect_measure_values`：純推送取值、timeout 放行、漏壓不寫值、寫 NG(1) 至 D501~D512、設 D513 bit15、跳警報；新增手動旗標。
- `config.py`: 新增可調的漏壓 timeout 設定（預設 3 秒）。
- `plc_comm.py`: 沿用既有 `set_d513_bit`（bit15）與判定結果寫入；無新增。
- **PLC 端**：無需改梯形圖。
- 量測時序（已確認）：一循環約 5~7 秒（1 次空槍 + N 次量測，N 由 PLC 設定預設 6，每次量不同耳溫套並由 OK/NG port 彈出）；觸發間隔足夠，新鮮度窗口不會跨輪誤判。握手：HMI 收齊判定→寫 PLC/LOG→將 D500/D515 歸 0→PLC 確認後彈套。
